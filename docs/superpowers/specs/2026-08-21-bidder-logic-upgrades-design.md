# Дизайн: апгрейд логики ставок (Проект 2, спек 1)

Дата: 2026-08-21
Статус: черновик на ревью

## Контекст

Биддер (`core/rules.py` + `worker.py`) в бою: два контура — fast (тормозит),
slow (двигает по TACoS). Конфиг с оверрайдами глобал→кампания→SKU
(`core/config_resolver.py`), редактор порогов в веб-панели на всех трёх уровнях,
hot-reload воркером каждый цикл. Проект 1 добавил per-product контроль
(дейпартинг + вкл/выкл) — здесь его НЕ трогаем.

Текущая механика движения ставки грубая:
- **Шаг фиксированный** `±max_bid_step` (2₸), максимум `max_changes_per_day`
  (3) в сутки → максимум ±6₸/день. Ставка неделями ползёт к нужной.
- **avg_cpc игнорируется** — движок не смотрит на реальную цену клика, хотя она
  уже приходит в `SkuReconciled.avg_cpc`. Ставка-потолок может быть задрана
  сильно выше реальной цены, и подъёмы тратятся впустую.
- **Спенд-кап = жёсткий обрыв**: `cost_today ≥ лимит → ставка в пол` до конца
  суток. Реклама глохнет днём, вечерний трафик теряется.

## Не входит (решено с владельцем)

- **buy_box-гейт** — НЕ нужен: продаём под своим брендом, на карточке всегда
  единственный продавец → всегда в buy box, гейт никогда не сработал бы.
- **Целевой TACoS от себестоимости/маржи** — НЕ нужен: владелец считает себес и
  целевой ДРР в своей юнит-таблице и задаёт целевой TACoS по товару вручную через
  существующий оверрайд `target_tacos_low/high` по SKU.
- **avg_cpc активный срез здоровой ставки** — НЕ входит: avg_cpc используем
  только как страж подъёма (см. #3), активно ставку не режем — риск потерять
  объём. Возможен отдельный спек позже.

## Цель

Три апгрейда движка. Все — чистая логика в `rules.py`, новых источников данных
нет (`avg_cpc`, `cost_today`, `buy_box` уже в `SkuReconciled`). Все пороги
**задаются из админки** (глобал/кампания/SKU), код держит только фолбэк-дефолты.

### #1 — Пропорциональный шаг ставки

Заменяем фиксированный шаг на процент от текущей ставки:

```
шаг = round(bid × bid_step_pct)
шаг = clamp(шаг, 1, max_bid_step)     # ≥ 1₸, ≤ кэп одного шага
new_bid = clamp(bid ± шаг, min_bid, bid_ceiling)
```

- Новый параметр **`bid_step_pct`** (дефолт **0.20**).
- **`max_bid_step`** меняет смысл: теперь «максимальный скачок за один шаг»
  (страховка от рывка). Дефолт **2 → 15**.
- **Escape-hatch:** `bid_step_pct = 0` → старое поведение (фиксированный шаг
  `max_bid_step`). Даёт мгновенный откат из UI без передеплоя.
- Округление до целого ₸; гарантированный сдвиг ≥ 1₸, чтобы подъём/срез не
  «залипал» из-за округления (кроме упора в пол/потолок — там `hold`, как сейчас).
- Применяется в ОБОИХ контурах (fast срез и slow raise/lower идут через общий
  `_stepped`).

### #3 — avg_cpc-хедрум (страж подъёма)

Только в slow-контуре, только на подъёме. Перед raise:

```
если avg_cpc > 0 и bid > avg_cpc × cpc_headroom  →  hold
    reason: «ставка {bid} уже > avg_cpc {avg_cpc} × {cpc_headroom} — подъём не нужен»
```

- Дефолт **`cpc_headroom = 2.0`**.
- Только глушит бессмысленные подъёмы. Активно ставку НЕ срезает — здоровую
  позицию не трогаем.
- **Escape-hatch:** `cpc_headroom = 0` → страж выключен (подъём как раньше).
- `avg_cpc == 0` (нет данных о цене клика) → страж не срабатывает, обычная логика.

### #5 — Пейсинг бюджета

Только в fast-контуре. Мягкий троттлинг ДО жёсткого стопа:

```
day_frac       = доля суток, прошедшая к текущему часу Алматы (0..1), считает worker
pace_limit     = лимит × day_frac × pace_tolerance
cost_today ≥ лимит       →  пауза (ставка в пол) — жёсткий стоп, как сейчас
cost_today ≥ pace_limit  →  снизить на один шаг (притормозить, не убить)
```

- Дефолт **`pace_tolerance = 1.25`** (25% слака, чтобы не душить рано утром).
- `лимит` — тот же, что у существующего спенд-капа (`daily_budget ×
  sku_budget_fraction`, фолбэк `daily_sku_cost_limit`).
- Троттлинг использует пропорциональный шаг (#1). Следующий тик переоценит: успел
  трафик успокоиться — fast больше не режет (fast никогда не поднимает; обратный
  подъём делает slow по TACoS).
- **Escape-hatch:** `pace_tolerance = 0` → пейсинг выключен, остаётся только
  жёсткий стоп (текущее поведение).
- `day_frac` передаётся в `evaluate_fast` параметром (дефолт 1.0 = без эффекта
  пейсинга) — `rules.py` остаётся чистым, время считает worker (как `daily_budget`).

## Порядок в fast-контуре (`_eval_fast_one`)

Приоритет предохранителей (сверху вниз). Защита бюджета (жёсткий стоп + пейсинг)
идёт ДО лимита изменений в сутки — иначе `max_changes_per_day=3` задушил бы
пейсинг (3 дёрганья/день). Обоснование то же, что у существующего жёсткого
спенд-капа: слив бюджета тормозим всегда. Пейсинг только СНИЖАЕТ и ограничен снизу
`min_bid`, поэтому освобождение от лимита изменений безопасно (в худшем случае
плавно доводит до пола — тот же исход, что жёсткий стоп, только мягче).

1. `product_state != Active` → hold.
2. `cost_today ≥ лимит` → пауза (жёсткий стоп; освобождён от лимита изменений).
3. `pace_tolerance > 0` и `cost_today ≥ pace_limit` → снизить на шаг (пейсинг;
   освобождён от лимита изменений).
4. `changes_today ≥ max_changes_per_day` → hold.
5. 0 корзин при достаточных кликах → срез.
6. Скачок avg_cpc относительно прошлого снапшота → срез.
7. Иначе hold.

Примечание по частоте PUT: пейсинг снижает максимум на один шаг за тик и
останавливается, как только траты падают ниже `pace_limit` или ставка упирается в
`min_bid` — churn самоограничивается, отдельный дневной лимит пейсинга не нужен
(YAGNI).

## Порядок в slow-контуре (`_eval_slow_one`)

Без изменений, кроме страж-проверки перед подъёмом:

1..3. Как сейчас (не Active / лимит изменений / TACoS None или > high → срез).
4. `TACoS < low` и `score ≥ min_score_for_raise`:
   - `cpc_headroom > 0` и `bid > avg_cpc × cpc_headroom` → **hold (страж avg_cpc)**.
   - иначе → raise на шаг.
5. Иначе hold (TACoS в коридоре).

## Данные / конфиг

Новые поля `RulesConfig` (в `core/rules.py`), дефолты = фолбэк:

```python
bid_step_pct: float = 0.20     # #1: доля шага от ставки; 0 = старый фикс-шаг
# max_bid_step: 2 → 15         # #1: смысл = кэп одного шага
cpc_headroom: float = 2.0      # #3: не поднимать, если bid > avg_cpc×это; 0 = выкл
pace_tolerance: float = 1.25   # #5: слак пейсинга; 0 = пейсинг выкл
```

`max_bid_step` дефолт меняется 2 → 15 в `RulesConfig` и в `config/rules.yaml`.

### Проводка в админку (ключевое требование владельца)

Все 4 параметра редактируются из веб-панели — как существующие пороги:

- **`core/config_resolver.py`**: добавить `bid_step_pct`, `cpc_headroom`,
  `pace_tolerance` в `OVERRIDABLE_FIELDS` (переопределение по кампании/SKU).
  `max_bid_step` там уже есть.
- **`core/settings_io.py`**: добавить те же 3 поля в `SETTINGS_FIELDS`, в
  `validate_settings` (правила ниже) и в словарь `save_settings`.
- **Форма UI** (`webui/templates/settings.html` и SKU/кампания-редакторы): поля
  появляются в форме порогов автоматически по `SETTINGS_FIELDS`/
  `OVERRIDABLE_FIELDS`, если шаблон итерирует список; если поля захардкожены —
  добавить строки ввода для трёх новых.
- Hot-reload воркером — существующий (читает `rules.yaml` каждый цикл).

### Валидация (`validate_settings`)

- `bid_step_pct`: число, `0 ≤ x < 1` (доля; 0 = выкл, 1+ бессмысленно).
- `cpc_headroom`: число, `≥ 0` (0 = выкл).
- `pace_tolerance`: число, `≥ 0` (0 = выкл).
- `max_bid_step`: существующее правило `≥ 1` сохраняется.

## Движок: worker

`worker.run_tick` для fast считает `day_frac` от `now` (Алматы) и передаёт в
`evaluate_fast(active, cfg_for, state, daily_budget, day_frac)`. Slow-контур
сигнатуру не меняет (страж avg_cpc берёт всё из `SkuReconciled`). Порядок слоёв
(дейпартинг из Проекта 1 → fast/slow) не меняется.

`day_frac` = `(секунды с полуночи Алматы) / 86400`, в `[0, 1)`.

## Безопасный выкат на боевую

- Каждый апгрейд выключается значением `0` из UI без передеплоя.
- Все пороги переопределяются по одному SKU → обкатка на канарейке, затем раскат.
- `dry_run` и per-product вкл/выкл (Проект 1) остаются как рубильники отката.
