# Настройки на уровне кампании/товара + свежесть данных дашборда

Дата: 2026-08-16
Статус: одобрено к реализации (после ревью спеки)

## Проблема

Сегодня всё тюнится одним плоским глобальным конфигом `config/rules.yaml`: одни и те
же 11 порогов движка применяются ко всем кампаниям и всем SKU. Владелец хочет
регулировать метрики **отдельно по каждой кампании и каждому товару**.

Плюс дашборд показывает живые цифры (просмотры/клики/расход/ставки/TACoS) только на
момент последнего цикла воркера, без индикации свежести — создаётся ощущение, что
данные «не в реальном времени».

## Решение (обзор)

Две независимые части, катятся по очереди:

1. **Иерархический конфиг (путь А — наследование):** общие настройки → отличия
   кампании → отличия товара. Переопределяется только то, что реально отличается;
   остальное наследуется сверху и автоматически подхватывает будущие изменения
   вышестоящего уровня.
2. **Свежесть данных:** метка «данные на HH:MM» на дашборде, кнопка «Обновить
   сейчас» (безопасный read-only пулл), ускорение фонового fast-цикла.

`dry_run` и `campaign_ids` (allowlist) остаются **только глобальными** — это
рубильники, не тюнинг.

---

## Часть 1 — Иерархический конфиг

### Поля, доступные к переопределению (11)

Все числовые пороги `RulesConfig`:
`target_tacos_low`, `target_tacos_high`, `daily_sku_cost_limit`,
`sku_budget_fraction`, `min_clicks_for_no_cart_cut`, `cpc_spike_pct`,
`max_bid_step`, `max_changes_per_day`, `bid_ceiling`, `min_bid`,
`min_score_for_raise`.

**Не переопределяются (global-only):** `dry_run`, `campaign_ids`.

### Хранение

- **Глобальные дефолты:** остаются в `config/rules.yaml` (без изменений формата).
- **Отличия (overrides):** новая таблица в существующей SQLite (`core/store.py`):

  ```sql
  CREATE TABLE IF NOT EXISTS config_overrides (
      scope    TEXT,     -- 'campaign' | 'sku'
      scope_id TEXT,     -- campaign_id или sku
      field    TEXT,     -- имя поля из 11 разрешённых
      value    TEXT,     -- значение как строка; типизируется при resolve
      user     TEXT,     -- кто менял
      ts       INTEGER,  -- когда
      PRIMARY KEY (scope, scope_id, field)
  );
  ```

  Отсутствие строки = поле наследуется. «Сброс к наследованию» = удаление строки.
  Изменения пишутся и в существующий `settings_audit` (кто/что/старое→новое).

### Резолвер эффективного конфига

Новый модуль/функция (например `core/config_resolver.py`):

```
resolve_config(store, global_cfg, campaign_id, sku) -> RulesConfig
```

Логика: копия `global_cfg` → накладываем overrides кампании → накладываем overrides
SKU. Только для 11 разрешённых полей. Значения из `config_overrides.value`
приводятся к типу поля (float/int) по образцу `RulesConfig`. `dry_run` и
`campaign_ids` всегда берутся из global (overrides их не касаются).

Кэш overrides на цикл, чтобы не читать БД на каждый SKU (аналогично тому, как
воркер уже читает cfg раз в цикл).

### Изменения в воркере (`worker.py`)

Сейчас `run_tick` зовёт `evaluate_fast/slow(products, ctx.cfg, ...)` с единым cfg на
все SKU кампании. Меняем на per-SKU резолв:

- В `run_tick` для каждого товара получаем `resolve_config(..., campaign_id, sku)`.
- Движок `core/rules.py` уже разложен на per-one (`_eval_fast_one`,
  `_eval_slow_one`) — им передаём индивидуальный cfg. `evaluate_fast/slow`
  оборачиваем так, чтобы принимать резолвер (или заранее собранную карту
  `sku -> cfg`), сохраняя чистоту движка (движок остаётся без сети/БД).
- `sku_budget_fraction` продолжает считаться от `daily_budget` кампании, но сама
  доля теперь может быть переопределена на уровне кампании/SKU.

### Изменения в БД для UI-списков

`products_snapshot` сейчас **не хранит `campaign_id`** — а он нужен, чтобы показать
список товаров конкретной кампании. Добавляем колонку `campaign_id` (миграция
`ALTER TABLE ... ADD COLUMN`, как уже сделано для `decisions_log`) и пишем её в
`save_products_snapshot` (значение прокидывается из `run_tick`, где `campaign_id`
известен). Новый метод стора: `get_campaign_skus(campaign_id)` — последние
уникальные SKU кампании с именем/ставкой из свежего снапшота.

### Изменения в UI (`webui/app.py`, `templates/`)

- **Глобальные настройки** — как есть (страница `/settings`).
- **Настройки кампании** — `GET/POST /settings/campaign/{campaign_id}`. Форма всех
  11 полей, предзаполненных **эффективным (унаследованным от глобала) значением**.
  У каждого поля бейдж «унаследовано» / «своё» и кнопка «сбросить к наследованию».
- **Настройки товара** — `GET/POST /settings/sku/{campaign_id}/{sku}`. То же, но
  предзаполнение эффективным значением с учётом уровня кампании; бейджи и сброс —
  аналогично.
- **Навигация:** на дашборде у строки кампании — ссылка «Настройки кампании»;
  на странице кампании — список её товаров со ссылкой «Настройки товара».
- Сохранение: пустое/не тронутое поле → наследуется (нет строки override);
  введённое значение, отличное от унаследованного → пишется override. Валидация
  переиспользует `validate_settings` из `core/settings_io.py`.

## Часть 2 — Свежесть данных

- **Метка времени:** дашборд показывает «данные на HH:MM» — время последнего
  снапшота (`MAX(ts)` из `products_snapshot`, формат в таймзоне Алматы).
- **Кнопка «Обновить сейчас»:** `POST /refresh` — разовый безопасный пулл
  (только чтение: `list_active_campaigns` + `get_campaign_products` → запись
  снапшота, **без** `update_bids`). Best-effort, как текущий `_get_campaign_budgets`:
  любая проблема с сессией/WAF гасится, дашборд не падает. После — редирект на
  дашборд со свежими данными.
- **Ускорение фонового цикла:** fast-джоба в `worker.py` с 20 мин → ~5 мин, чтобы
  данные были свежими и без ручной кнопки. (Значение вынести/подтвердить при
  реализации; следить за нагрузкой на сессию кабинета.)

### Замечание по конкуренции за сессию

И воркер, и кнопка «Обновить», и пулл бюджетов дашборда используют одну
Playwright-сессию кабинета (за WAF). Живой пулл делаем строго best-effort и
редким по своей природе (ручная кнопка + кэш бюджетов 60с уже есть). Не тянем
вживую на каждом открытии дашборда — только по кнопке.

## Тестирование

Как в проекте — plain-script тесты (без pytest), запуск через `.venv`:

- **Резолвер:** глобал без overrides = глобал; override кампании перекрывает
  глобал; override SKU перекрывает и глобал, и кампанию; удаление override =
  возврат к наследованию; типизация значений; global-only поля (`dry_run`,
  `campaign_ids`) не переопределяются.
- **Стор:** CRUD `config_overrides`; миграция `campaign_id` в `products_snapshot`;
  `get_campaign_skus`.
- **Воркер:** два SKU с разными эффективными конфигами дают разные решения в одном
  цикле (посевные снапшоты, `dry_run`).
- **WebUI:** страницы кампании/SKU рендерятся с предзаполнением и бейджами;
  сохранение пишет/удаляет override; сброс к наследованию; `POST /refresh`
  best-effort не падает при недоступной сессии; метка времени рендерится.

## Порядок реализации

1. Часть 1: стор (таблица + миграция + методы) → резолвер → воркер → UI.
2. Часть 2: метка времени → кнопка обновления → ускорение fast-цикла.

Каждая часть самостоятельна и мержится отдельно.

## Явно вне рамок (YAGNI)

- Массовое редактирование настроек нескольких товаров разом.
- Импорт/экспорт конфигов, шаблоны настроек.
- WebSocket/пуш живого обновления дашборда без перезагрузки.
- Переопределение `dry_run`/`campaign_ids` по кампаниям.
