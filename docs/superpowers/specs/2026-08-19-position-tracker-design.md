# Трекер позиций Kaspi — дизайн

Дата: 2026-08-19
Статус: согласован (ждёт финального ревью спеки)

## Проблема и цель

Нужно отслеживать **неперсонализированную («абсолютную») позицию нашего товара**
в поисковой выдаче Kaspi по ключевым словам (напр. «аэрогриль») — где мы стоим
сверху вниз, и кто стоит выше нас. Персональный поиск на устройстве искажает
позиции; нам нужна выдача без авторизации и без кликов.

Выдача Kaspi устроена как чередование: рекламные карточки (PCM) и органика.
Обе части важны:
- **органическая позиция** нашего товара по городам;
- **рекламные слоты** — воспроизвести картину «2 рекламных / 4 органика», где
  именно стоит наш промо-товар и кто рекламируется выше.

## Ключевые факты (проверено эмпирически 2026-08-18)

- Эндпоинт `GET https://kaspi.kz/yml/product-view/pl/filters` отдаёт JSON с
  **органической выдачей** (`data.cards`) в точном порядке сверху вниз.
  Параметры реального запроса сайта:
  `text=<кириллица urlencoded>&page=<n>&all=false&fl=true&ui=d&q=:availableInZones:<zone>&i=-1&c=<cityId>`.
  Пагинация по 12 карточек, `data.total` = общее число (напр. 2697 по «аэрогриль»).
  Город задаётся параметром `c` (cityId, напр. `750000000` = Алматы) и зоной
  доставки `q=:availableInZones:<zone>` (напр. `Magnum_ZONE1`).
- **UA обязателен браузерный.** С User-Agent приложения Kaspi эндпоинт отвечает
  **403** (WAF). App ходит на свой мобильный API, не сюда.
- В JSON есть слоты под рекламу: `data.promotedCards`, `data.promotedItems`,
  `data.promotedByPcm`. В web-контексте они **всегда пустые** (null/false).
  Перебор `ui=d/m/i/a` рекламу не включает. Десктопный сайт вживую рекламу
  **не показывает вообще** — только органику с пагинацией.
- Вывод: **реклама (PCM) приходит отдельным запросом, который делает только
  мобильное приложение.** Голым HTTP её пока воспроизвести нельзя — нужен
  разовый перехват (см. Часть B).

## Вводные от владельца

- Города: **Алматы и Астана** (список в конфиге, расширяемый).
- Вывод: **в существующий дашборд** (`webui` + текущая БД).
- Частота: **раз в 15 минут** (по HTTP — легко). Для рекламы через чтение
  экрана эмулятора такая частота нереальна — там будет реже (см. B).
- Порядок работ: **сперва Часть A (органика), затем обязательно Часть B (реклама).**

## Архитектура

Две части. **A строится сейчас** (доказано, что HTTP работает). **B — спайк
и развилка** после A.

### Часть A. Органический трекер (HTTP)

Модульные границы держим в стиле проекта: HTTP+парсинг отдельно от БД, БД
отдельно от оркестрации, оркестрация отдельно от отображения.

#### A1. `connectors/search_client.py` — сбор и парсинг (не знает про БД)

- Функция вида `fetch_listing(keyword, city_id, zone, max_depth) -> Listing`.
- Ходит на `filters` с **браузерным UA** (переиспользуем `BROWSER_UA` из
  существующих клиентов — держать синхронно), листает страницы по 12, пока не
  найдёт наш товар или не упрётся в `max_depth` (напр. топ-100).
- Возвращает упорядоченный список карточек: `rank` (1-based, сквозной по
  страницам), `product_id` (`configSku`), `title`, `price`, `brand`,
  `merchant`(если есть) — и `total`.
- **Никакой персонализации**: без cookies/токенов, чистый запрос.
- Ретраи/таймауты в стиле `merchant_client.py` (httpx, backoff).

#### A2. Идентификация «нашего товара»

- Наш товар — это **карточка Kaspi (мастер-продукт)**, на которой стоит наш
  оффер. Опознаём по `product_id` (`configSku`).
- Конфиг маппит `keyword → our_product_id`. `our_product_id` берём из ссылки на
  карточку Kaspi (хелпер `resolve_product_id_from_url`) либо сшиваем с
  существующими merchantSku проекта (уточняется при наполнении конфига).

#### A3. Конфиг

Отдельный файл в `config/` (напр. `positions.yaml`):
```yaml
cities:
  - {name: "Алматы", city_id: "750000000", zone: "Magnum_ZONE1"}
  - {name: "Астана", city_id: "710000000", zone: "<добыть с сайта>"}
track:
  - {keyword: "аэрогриль", product_id: "134653775", label: "Наш аэрогриль"}
max_depth: 100
```
Зона-токен (`availableInZones`) для каждого города добывается один раз с сайта
(GET страницы поиска в нужном городе → из URL `q=:availableInZones:<zone>`).
Собрать эти токены — отдельный подшаг наполнения конфига.

#### A4. Хранение — новая таблица в `core/store.py`

В стиле существующих таблиц (plain sqlite3, `_init_schema`):
```
CREATE TABLE IF NOT EXISTS position_snapshots (
    ts INTEGER, keyword TEXT, city TEXT, product_id TEXT,
    our_rank INTEGER,            -- NULL если вне top max_depth
    total INTEGER,
    listing_json TEXT            -- топ-N карточек (id/title/price/merchant/is_ad)
);
CREATE INDEX IF NOT EXISTS ix_pos_kw_city_ts
    ON position_snapshots(keyword, city, ts);
```
`listing_json` — сериализованный топ-N (напр. первые 24–48), чтобы дашборд
показал «кто выше нас» без повторного обхода. `is_ad` пока всегда false
(заполнится в Части B).

Методы `Store`: `put_position_snapshot(...)`, `get_position_series(keyword, city)`,
`get_latest_listing(keyword, city)`.

#### A5. Оркестрация — job в `worker.py`

- Новая чистая функция `run_position_tick(ctx)` (тестируется с фейковым
  `search_client` и фейковым `store`, как остальные тики).
- Проходит по всем `(keyword × city)` из конфига, зовёт `fetch_listing`,
  пишет снапшот. Время — в Алматы (как в проекте, `ALMATY`).
- Регистрация расписания (каждые 15 мин) — только в `main()` через APScheduler,
  рядом с существующими job'ами.

#### A6. Дашборд — `webui`

Новая секция/страница:
- по каждому `keyword × city`: текущий `our_rank`, спарклайн динамики во времени;
- таблица топ-N сверху вниз с подсветкой нашей карточки; колонка «реклама/органика»
  (готова к Части B, пока вся органика).
- Время отображаем в Алматы (как уже сделано в дашборде).

### Часть B. Рекламные позиции — спайк, затем развилка

#### B1. Спайк (time-boxed, на эмуляторе)

1. Android-эмулятор на Mac (образ с root-доступом, напр. Google APIs).
2. Установить приложение Kaspi (sideload APK или через Play-образ).
3. mitmproxy + системный CA; поиск «аэрогриль»; поймать запрос, заполняющий
   рекламные слоты (PCM): URL, заголовки, тело, наличие подписи/токена.
4. **Учитываем реальность:** Kaspi — банк, вероятны cert-pinning и детект
   рута/эмулятора. Спайк ограничен по времени; при упоре в пиннинг — фиксируем
   факт и переходим к развилке B3.

#### B2. Развилка «не запиннено» → HTTP-реклама

- Добавляем ад-эндпоинт в `search_client`, мёржим `promotedCards`/`promotedItems`
  с флагом `is_ad=true`, реконструируем чередование «2 рекл / 4 органика».
- Всё по HTTP, частота 15 мин, эмулятор **выбрасываем** после спайка.

#### B3. Развилка «запиннено» → чтение экрана эмулятора

- Отдельный медленный сборщик: гоняем приложение в эмуляторе, вводим keyword,
  читаем отрисованный список через **accessibility-дерево** приложения
  (UIAutomator/Appium), не пиксели/OCR.
- Эмулятор остаётся жить постоянно. Частота ниже (напр. пара раз в день,
  меньше городов — по одному городу за раз). Органика при этом продолжает
  идти 15 мин по HTTP (Часть A не трогаем).
- Пишем в те же `position_snapshots` с `is_ad`.

## Тестирование

- `search_client`: юнит-тесты парсинга на сохранённом реальном JSON-ответе
  (фикстура), включая случаи «товар не найден в top N» и пагинацию.
- `store`: запись/чтение снапшота и серии (как `test_store.py`).
- `worker`: `run_position_tick` с фейками (как `test_worker.py`).
- webui: рендер новой секции с фейковыми снапшотами (как `test_webui.py`).
- Стиль тестов проекта: плоские скрипты, без pytest (см. память dev-env).

## Обработка ошибок

- 403/блок WAF → лог + пропуск тика (не роняем воркер), алерт в лог.
- Товар вне top `max_depth` → `our_rank = NULL` (это валидный результат, «глубоко»).
- Таймаут/сеть → ретрай с backoff, затем пропуск среза.
- Смена схемы ответа Kaspi (нет `data.cards`) → защитный парсинг, лог-варнинг.

## Явно вне скоупа (YAGNI)

- Постоянный эмулятор — только если B1 покажет пиннинг.
- OCR/чтение пикселей — не делаем, только accessibility-дерево если дойдём до B3.
- Изменение логики ставок — трекер только наблюдает, в автопилот не вмешивается
  (на этом этапе).

## Порядок реализации

1. Часть A целиком (A1→A6), запуск в дашборде, 15-мин срез по нескольким городам.
2. Часть B: спайк B1 → развилка B2 или B3.
