# Глобальный настраиваемый период TACoS (`tacos_window_days`)

**Дата:** 2026-08-28
**Статус:** утверждён, готов к плану

## Проблема

Окно расчёта TACoS зашито как `window_days = 2` в дефолте `WorkerContext`
(`worker.py`). Хуже того — в `build_ctx()` это поле **не передаётся**, поэтому
воркер всегда работает с окном 2 дня, и изменить его нельзя нигде, кроме правки
кода.

Владелец хочет управлять этим периодом (типовые значения 2 / 7 / 30 дней, плюс
произвольное число дней) и чтобы выбор **влиял на логику биддера**, а не только на
отображение.

## Решение (область и границы)

Период TACoS становится **глобальным** параметром конфига — одно значение на весь
автопилот. Оно меняет поведение биддера: за сколько дней собирается выручка и
расход, по какому TACoS движок двигает ставки (медленный контур). Дашборд
автоматически отражает это окно, т.к. воркер пишет `tacos_daily` под сегодняшней
датой именно за это окно.

**Осознанно НЕ делаем** (по решению владельца «только глобально»):

- нет оверрайдов периода на кампанию/SKU;
- нет переделки revenue-цикла на посуточное хранение cost/revenue;
- нет отдельного «view-дропдауна» на дашборде, пересчитывающего произвольный
  исторический период.

## Как сейчас устроено (контекст)

- `WorkerContext.window_days: int = 2` — дефолт датакласса (`worker.py`).
- `build_ctx()` (`worker.py:~304`) создаёт `WorkerContext(...)` **без** `window_days`
  → всегда 2.
- Использование `window_days`:
  - `run_revenue_cycle` → `RevenueCollector.collect(window_days=ctx.window_days)` —
    сколько дней заказов обходить в Shop API;
  - `run_tick` / `run_cycle` → `_almaty_dates(ctx.window_days, now)` — окно расхода
    из кабинета маркетинга;
  - дальше `reconcile` считает `tacos = cost / revenue` за это окно и пишет в
    `tacos_daily[today]` (перезаписывается каждый тик).
- Глобальные настройки живут в `config/rules.yaml`, редактируются через
  `core/settings_io.py` (`load_settings` / `validate_settings` / `save_settings`),
  поля перечислены в `SETTINGS_FIELDS`. Воркер перечитывает `rules.yaml` каждый цикл
  через `load_cfg_safe` (hot-reload без рестарта). Датакласс порогов — `RulesConfig`
  (`core/rules.py`).
- Форма настроек (`webui/templates/settings.html`) рендерит все поля из `fields`
  как `type="number"`, кроме особо обработанных `dry_run` и `campaign_ids`.

## Изменения (5 точек)

### 1. `core/rules.py` — новое поле
Добавить в `RulesConfig`:
```python
tacos_window_days: int = 2   # окно расчёта TACoS (дни) для биддера
```
Дефолт 2 сохраняет текущее поведение при отсутствии значения в yaml.

### 2. `core/settings_io.py` — валидация и запись
- Добавить `"tacos_window_days"` в `SETTINGS_FIELDS` (в разумном месте порядка формы,
  например рядом с TACoS-порогами).
- В `validate_settings`: значение — **целое число в диапазоне [1, 90]**. Дробное,
  не-число, < 1 или > 90 → ошибка. (Верхний предел 90 защищает от случайного «365»,
  который надолго повесит обход заказов Shop API.)
- В `save_settings`: писать как `int(float(data["tacos_window_days"]))` (по образцу
  `min_clicks_for_no_cart_cut` / `max_changes_per_day`).

### 3. `worker.py` `build_ctx()` — связать настройку с логикой
В создании `WorkerContext(...)` передать:
```python
window_days=cfg.tacos_window_days,
```
Единственная строчка, соединяющая настройку с реальным поведением: revenue-цикл и
окно расхода начинают считать за выбранный период.

### 4. `webui/templates/settings.html` — ввод периода
Поле «Окно TACoS, дней»: `type="number"` (min=1, max=90, step=1) с нативным
`<datalist>` пресетов **2 / 7 / 14 / 30**. Это даёт и выпадающие пресеты, и ввод
произвольного числа — без JS.

Метка/подсказка через `field_meta`:
- label: «Окно TACoS, дней»
- hint: «За сколько дней считать TACoS для решений биддера. Больше дней = стабильнее,
  но реакция медленнее; 30 дней заметно нагружает обход Shop API.»

Т.к. общий цикл рендерит числовые поля автоматически, для datalist поле надо
особо-обработать (как `campaign_ids`): вывести `<input list="...">` + `<datalist>`.

### 5. Дашборд — показать окно
- `webui/app.py` route `dashboard`: прочитать `tacos_window_days` из текущего конфига
  (тем же способом, что читаются настройки для отображения) и передать в шаблон.
- `webui/templates/dashboard.html`: подпись секции «TACoS по SKU» / текст «за сегодня»
  заменить на «за последние N дн.», где N — переданное окно.

## Тесты

- `test_settings_io.py`:
  - валидное значение (например 7) проходит;
  - `0`, `91`, `2.5`, нечисло → ошибка валидации;
  - round-trip: `save_settings` → `load_settings` возвращает сохранённое окно.
- Воркер/wiring: `build_ctx()` (или эквивалент) прокидывает `window_days` из
  `cfg.tacos_window_days`, а не дефолт датакласса. Если прямой тест `build_ctx`
  затруднён (лезет в env/сеть), проверить на уровне: `RulesConfig(tacos_window_days=7)`
  → `WorkerContext(..., window_days=cfg.tacos_window_days).window_days == 7` и что
  `run_revenue_cycle`/`_almaty_dates` используют его (есть существующие тесты воркера
  для образца).

## Критерии приёмки

1. В форме настроек есть поле «Окно TACoS, дней» с пресетами 2/7/14/30 и вводом
   произвольного числа.
2. Сохранение периода пишет `tacos_window_days` в `config/rules.yaml`; невалидные
   значения (< 1, > 90, дробные) отклоняются с понятной ошибкой.
3. Воркер на следующем цикле считает выручку/расход/TACoS за выбранное окно (без
   рестарта).
4. Дашборд подписывает секцию TACoS выбранным числом дней.
5. Все существующие тесты зелёные + новые тесты валидации/wiring проходят.
