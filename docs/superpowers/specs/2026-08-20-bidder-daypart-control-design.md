# Дизайн: контроль биддера по товару — дейпартинг + вкл/выкл

Дата: 2026-08-20
Статус: черновик на ревью

## Контекст

Биддер (`core/rules.py` + `worker.py`) уже в бою: два контура (fast — тормозит,
slow — двигает по TACoS), конфиг с оверрайдами глобал→кампания→SKU
(`config_overrides`), аудит-лог решений, `dry_run`-предохранитель с тумблером в
UI. Веб-панель уже умеет: редактор порогов на всех трёх уровнях
(`/settings`, `/settings/campaign/..`, `/settings/sku/..`), тумблер `dry_run`,
лог решений по товару (`/decisions/{sku}`).

Не хватает управления биддером **на уровне отдельного товара во времени**:
владелец хочет задавать, **когда** биддер работает по товару (дейпартинг) и
**трогает ли** он товар вообще (вкл/выкл — роль «канарейки» при выходе в бой).

## Цель

Дать per-product контроль:
1. **Дейпартинг** — рабочее окно (часы + дни недели, Алматы). Вне окна биддер
   принудительно ставит ставку в `min_bid` (рекламу НЕ выключаем — просто
   минимальная ставка). В окне — обычная логика fast/slow.
2. **Вкл/выкл по товару** — выключенный товар биддер не трогает вообще
   (последняя ставка замораживается). Default для нового товара — **enabled**
   (сохраняет текущее поведение: бот уже в бою на всех товарах).
3. **Кнопка «Проверить сейчас»** — мгновенный dry-пересчёт решения по товару с
   причиной, ничего не отправляет.

Явно НЕ входит (YAGNI / уже есть):
- Отдельный kill-switch — им служит существующий тумблер `dry_run` (щёлкнул →
  следующий цикл не шлёт реальных PUT). Сделаем его заметнее на дашборде.
- Логика ставок (пропорциональный шаг, buy_box-гейт, avg_cpc-хедрум, целевой
  TACoS от маржи, пейсинг) — это отдельный Проект 2, следующий спек.
- Себестоимость/маржа per-product — придёт с Проектом 2 (там же и поле в UI).

## Данные

Новая таблица (отдельно от `config_overrides`, чтобы не смешивать пороги с
управлением):

```sql
CREATE TABLE IF NOT EXISTS product_control (
    campaign_id  TEXT,
    sku          TEXT,
    enabled      INTEGER DEFAULT 1,   -- 0/1: трогает ли биддер этот товар
    window_start INTEGER DEFAULT 0,   -- час начала окна, Алматы, 0..23
    window_end   INTEGER DEFAULT 24,  -- час конца окна (эксклюзивно), 1..24
    days_mask    INTEGER DEFAULT 127, -- битовая маска дней недели, Пн..Вс = биты 0..6; 127 = все
    user         TEXT,
    ts           INTEGER,
    PRIMARY KEY (campaign_id, sku)
);
```

Дефолт «нет записи» = enabled, окно 0..24 каждый день (полностью прозрачно —
поведение как сейчас). `window_end` эксклюзивен: `[start, end)`. Окно
«круглосуточно» = 0..24. Пустое/инвертированное окно (`start >= end`)
валидируется в UI и не сохраняется.

### Методы Store

- `get_product_control(campaign_id, sku) -> ProductControl` — запись или дефолт.
- `set_product_control(campaign_id, sku, enabled, window_start, window_end, days_mask, user, ts)` — upsert.
- `list_product_control(campaign_id) -> dict[sku, ProductControl]` — для дашборда
  (батчом, без N запросов).

`ProductControl` — dataclass с полями таблицы + метод
`active_at(dt) -> bool` (enabled И день в маске И час в `[start, end)`), чтобы
логика «активно ли сейчас» жила в одном месте и тестировалась изолированно.

## Движок: контрольный слой

`rules.py` остаётся ЧИСТЫМ (без времени/БД). Дейпартинг применяется в
`worker.run_tick` **до** `evaluate_fast/slow`, т.к. worker уже владеет временем
(`now_fn`) и стором.

Порядок в `run_tick` (после чтения products, до обычной оценки):

1. Загрузить контроль батчом: `controls = store.list_product_control(campaign_id)`.
2. Разбить products на три группы по `control.active_at(now)` / `enabled`:
   - **disabled** → синтетическое решение `hold`, reason
     «биддер выключен для товара» — правила не гоняем.
   - **вне окна** (enabled, но `active_at(now) == False` из-за времени/дня) →
     решение `lower` с `new_bid = effective_min_bid(sku)`, reason
     «вне рабочего окна (ЧЧ–ЧЧ, дни …) → ставка в пол»; если ставка уже в полу —
     это `hold` (как в существующем `_stepped`). Правила не гоняем.
   - **активные** → как сейчас: `evaluate_fast/slow` c `cfg_for`.
3. Слить решения (контрольные + обычные) и передать в `_apply_and_log` — единый
   аудит и применение (ставка-в-пол применяется тем же `update_bids`, что и
   pause сейчас).

`effective_min_bid(sku)` берётся из того же резолвера конфига
(`resolve_config` → `RulesConfig.min_bid`), что и в правилах, чтобы per-SKU
оверрайд `min_bid` учитывался и вне окна.

Реализация: вынести разбиение в чистую функцию
`split_by_control(products, controls, now, min_bid_for) -> (active, control_decisions)`
(тестируется без сети), `run_tick` только склеивает.

## UI

### Экран товара `/settings/sku/{campaign_id}/{sku}`

Добавляем блок «Управление и расписание» над/под существующим блоком порогов:

- тумблер **«Биддер активен для товара»** (`enabled`);
- **окно**: два `select`/`number` — «с ЧЧ» и «до ЧЧ» (0..24, Алматы);
- **дни недели**: 7 галочек Пн..Вс (по умолчанию все);
- кнопка **«Сохранить расписание»** (отдельная форма → `POST /settings/sku/{cid}/{sku}/control`);
- кнопка **«Проверить сейчас»** → `POST /settings/sku/{cid}/{sku}/preview`:
  сервер делает dry-прогон (читает текущие products за окно, reconcile, прогоняет
  контрольный слой + правила по этому SKU) и показывает решение (action + reason)
  инлайн. Ничего в кабинет НЕ шлёт, в аудит НЕ пишет.

Валидация окна и маски — в существующем стиле `settings_io.validate_*`
(инвалидное окно → список ошибок над формой, не сохраняем).

### Дашборд `/`

- Колонка-индикатор статуса товара: **активен** / **вне окна** / **выключен**
  (вычисляется `control.active_at(now)`).
- Тумблер `dry_run` продублировать заметной плашкой сверху (режим боя виден сразу).
