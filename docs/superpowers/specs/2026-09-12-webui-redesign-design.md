# Редизайн веб-панели: React SPA, метрики по товарам, ИИ-помощник

Дата: 2026-09-12
Статус: согласовано, готово к написанию плана

## Зачем

Текущая панель (Jinja + рукописный CSS) не устраивает владельца ни визуально,
ни по структуре. Управление настройками живёт на уровне кампании, хотя решения
принимаются по товарам. Нет графиков, нет CTR/CR/ROAS, ИИ-аналитик пишет в лог,
который никто не читает.

Панель управляет реальным рекламным бюджетом — значит ядро решений
(`core/rules.py`, `core/config_resolver.py`, воркер) трогаем минимально, а
переписываем только слой представления.

## Что решено

| Вопрос | Решение |
|---|---|
| Главный экран | Список товаров с раскрывающейся панелью; кампания — фильтр, не экран |
| Настройки кампании | Экран удаляется; уровень в резолвере **остаётся** |
| Позиционный трекер | Удаляется **полностью** (код, таблица, конфиг, тесты) |
| Источник ROAS | Оба: реальная выручка Shop API (главное число) + GMV кабинета (рядом) |
| Стек фронта | React + Vite + TypeScript (SPA), FastAPI становится JSON API |
| Сборка и выкат | GitHub Actions собирает, кладёт в orphan-ветку `ui-dist` |
| ИИ | Кнопка «Разобрать товар» + ежедневный разбор на главной |
| Визуальный стиль | Apple: светлый, воздушный. Эталон — утверждённый макет |

Эталон дизайна: https://claude.ai/code/artifact/8731b2d2-0d72-4f26-8436-e0504c2fee32
Исходник макета сохранён в `docs/design/autopilot-mockup.html`.

## Ограничение, определившее половину дизайна

`MarketingClient.get_campaign_products(campaign_id, start_date, end_date)`
возвращает `views, clicks, carts, transactions, gmv, ctr, cr, crr, cost`
**за весь период запроса целиком**, а не по дням. Сейчас период равен
`tacos_window_days` (по умолчанию 2). Единственная честная «сегодняшняя»
величина — `costToday`.

Следствия:

1. Подневные ряды CTR/CR/ROAS нельзя получить из текущего потока данных.
   Нужен отдельный запрос со `StartDate = EndDate = <день>`.
2. `tacos_daily.cost` и `.revenue` — это **значение скользящего окна на конец
   дня**, а не расход за день. Для графиков по дням этот источник не годится;
   для текущего состояния — годится и остаётся.
3. История CTR/CR/ROAS начнётся с момента выката. Задним числом её нет.

### Авторизация

Не меняется: та же кука-сессия (`SessionMiddleware`, `https_only=True`,
`max_age=8ч`). SPA ходит с `credentials: "include"`. Токенов в `localStorage`
нет — XSS не уносит сессию.

Одно изменение: добавить `same_site="strict"`. SPA и API на одном origin, так
что кросс-сайтовые POST-запросы панели не нужны, а строгий режим закрывает CSRF
без отдельного токена.

Неавторизованный запрос к `/api/*` отдаёт `401 JSON`, а не редирект — редирект
на HTML-логин ломает `fetch`. Фронт на 401 показывает экран логина.

### Отдача SPA

`GET /` и любой неизвестный путь без префикса `/api` и `/static` отдают
`index.html` (клиентский роутинг). `/static/dist` монтируется как статика.

Dev: Vite на :5173 с прокси `/api` → :8000. Прод: FastAPI отдаёт собранный
`dist`, Caddy не меняется.

## Изменения в данных

### 1. `products_snapshot` — новые колонки

Добавить: `views INTEGER, ctr REAL, cr REAL, crr REAL, gmv REAL,
transactions INTEGER, buy_box INTEGER`.

Все семь полей уже приходят в `CampaignProduct` и сейчас выбрасываются.
Миграция — тем же паттерном `PRAGMA table_info` + `ALTER TABLE`, который уже
применён в `_init_schema` для `campaign_id`. `save_products_snapshot` пишет их.

### 2. `metrics_daily` — новая таблица

```sql
CREATE TABLE IF NOT EXISTS metrics_daily (
    day          TEXT,
    campaign_id  TEXT,
    sku          TEXT,
    merchant_sku TEXT,
    cost         REAL,   -- расход за этот день (кабинет)
    gmv          REAL,   -- GMV кабинета за этот день
    views        INTEGER,
    clicks       INTEGER,
    carts        INTEGER,
    transactions INTEGER,
    ctr          REAL,
    cr           REAL,
    revenue      REAL,   -- реальная выручка Shop API за этот день
    tacos        REAL,   -- cost / revenue
    roas         REAL,   -- revenue / cost
    roas_gmv     REAL,   -- gmv / cost
    ts           INTEGER,
    PRIMARY KEY (day, sku)
);
```

`tacos`, `roas`, `roas_gmv` хранятся посчитанными, а не выводятся на лету:
графики читают таблицу напрямую, и пересчёт при каждом рендере — лишняя работа.

`NULL` пишем только там, где ноль в **знаменателе** — величина не определена:
`tacos` при нулевой выручке, `roas` и `roas_gmv` при нулевом расходе. А вот
расход без выручки даёт честный `roas = 0.0`, и прятать его в `NULL` нельзя:
«потратили и не продали» — это сигнал, а не дырка в данных. Отдельно
`revenue = NULL` означает «Shop API за этот день ещё не опрашивали» — тогда
`roas` действительно неизвестен.

### 3. `ai_insights` — новая таблица

```sql
CREATE TABLE IF NOT EXISTS ai_insights (
    kind       TEXT,     -- 'product' | 'daily'
    scope_id   TEXT,     -- sku для 'product', '' для 'daily'
    day        TEXT,
    ts         INTEGER,
    text       TEXT,
    model      TEXT,
    tokens_in  INTEGER,
    tokens_out INTEGER,
    calls      INTEGER DEFAULT 1,
    PRIMARY KEY (kind, scope_id, day)
);
```

`calls` инкрементится при каждой перезаписи строки. Без него лимит
`AI_DAILY_LIMIT` протекал бы: `?force=1` перезаписывает строку того же дня, и
принудительные пересчёты были бы для лимита бесплатными, хотя деньги за вызов
уже заплачены.

## Новый воркер-джоб: подневные метрики

`daily_metrics_job` в `worker.py`, раз в час:

1. Для каждой ведомой кампании и для каждого из двух дней (сегодня и вчера):
   `get_campaign_products(campaign_id, day, day)` — чистые цифры кабинета за день.
2. Реальная выручка за тот же день — через новый метод
   `RevenueCollector.collect_for_day(day)`, который строит окно
   `[день 00:00, день 23:59:59]` по Алматы поверх уже существующей
   `almaty_window_ms`-логики и переиспользует тот же парсинг заказов.
3. Upsert в `metrics_daily`.

Вчера пересчитываем, потому что заказы отменяют задним числом и выручка за
вчерашний день продолжает меняться.

Стоимость: +1 запрос к маркетингу на кампанию на день (2 в час на кампанию) и
+1 к Shop API на день. На фоне текущих fast-тиков каждые 5 минут это шум.

Флаг `DAILY_METRICS_ENABLED` (дефолт вкл) — по образцу существующих флагов.

## JSON API

Все ответы — JSON. Все ошибки — `{"errors": ["..."]}` с осмысленным кодом.

| Метод и путь | Что делает |
|---|---|
| `POST /api/login` | логин, ставит куку |
| `POST /api/logout` | сброс сессии |
| `GET /api/me` | `{user}` или 401 |
| `GET /api/campaigns` | кампании + дневные бюджеты (кэш 60с, как сейчас) |
| `GET /api/overview?campaign&days` | KPI-строка: расход, выручка, GMV, TACoS, ROAS, ROAS по GMV, клики, корзины |
| `GET /api/products?campaign&days` | строки списка + ряд ставки для спарклайна |
| `GET /api/products/{cid}/{sku}?days` | эффективный конфиг, флаги «своё», расписание, свежие решения |
| `GET /api/products/{cid}/{sku}/series?days` | ряды для графиков, см. ниже |
| `PUT /api/products/{cid}/{sku}/settings` | оверрайды товара (значение или «наследовать») |
| `PUT /api/products/{cid}/{sku}/control` | вкл/выкл, рабочее окно, дни недели |
| `POST /api/products/{cid}/{sku}/preview` | «что бот сделает сейчас», ничего не отправляя |
| `GET`/`PUT /api/settings` | глобальные настройки (`config/rules.yaml`) |
| `POST /api/dry-run` | переключение тестового режима |
| `POST /api/refresh` | ручной снапшот |
| `GET /api/audit` | аудит изменений настроек |
| `POST /api/ai/product/{cid}/{sku}` | разбор товара |
| `GET /api/ai/digest?day` | ежедневный разбор |

Валидация настроек остаётся в `core/settings_io.py` и в существующей проверке
`min_bid <= bid_ceiling` — переносим вызовы, а не логику.

### Ответ `/series` — две разные шкалы времени

Это единственное место в API, где смешиваются два источника с разной
частотой, поэтому они лежат в **раздельных массивах**, а не в одной таблице
точек. Складывать их в общую сетку нельзя: тиков за день несколько, а дневная
метрика одна.

```jsonc
{
  "ticks": [                       // из products_snapshot, по тикам воркера
    { "ts": 1757000000, "bid": 32.0, "avg_cpc": 23.0 },
    { "ts": 1757003600, "bid": 34.0, "avg_cpc": 24.1 }
  ],
  "daily": [                       // из metrics_daily, по дням Алматы
    { "day": "2026-08-30", "cost": 2800, "revenue": 11429, "gmv": 14000,
      "views": 7333, "clicks": 88, "carts": 1, "transactions": 1,
      "tacos": 0.245, "roas": 4.08, "roas_gmv": 5.0,
      "ctr": 0.012, "cr": 0.011 }   // null там, где ноль в знаменателе
  ],
  "decisions": [                   // маркеры на графике ставки
    { "ts": 1757003600, "action": "raise", "old_bid": 32.0,
      "new_bid": 34.0, "reason": "cart-rate выше цели" }
  ],
  "corridor": { "low": 0.08, "high": 0.18 }   // эффективные границы TACoS
}
```

Массив точек, а не колоночные массивы: именно в таком виде данные потребляют
и графические библиотеки, и рукописный SVG — иначе фронту пришлось бы на
каждый рендер сшивать параллельные массивы обратно в точки. Поле называется
`avg_cpc`, а не `cpc`: так оно называется во всём остальном проекте — в
`CampaignProduct`, в `products_snapshot` и в правилах.

`daily` несёт больше полей, чем нужно графику TACoS: те же точки питают
графики CTR, конверсии и денег, и второй запрос за ними был бы лишним.

График ставки и CPC рисуется по `ticks`, графики TACoS/CTR/CR — по `daily`,
`corridor` даёт залитую полосу на графике TACoS.

⚠️ **Ловушка для реализации `daily`.** Ключ `metrics_daily` —
`(day, campaign_id, sku)`, и у товара, который ведётся в двух кампаниях, на
один день приходится ДВЕ строки. При этом `revenue`, `tacos` и `roas` в обеих
строках одинаковы: выручка приходит из Shop API по `merchant_sku` и к
кампаниям не привязана. Суммировать их по кампаниям нельзя — задвоятся.
Суммировать можно только `cost`, `clicks`, `views`, `carts`, `gmv`.

⚠️ **Атрибуция выручки при фильтре по кампании.** Выручка приходит из Shop
API по `merchant_sku` и к кампаниям не привязана в принципе. Поэтому если
товар рекламируется в двух кампаниях, а пользователь отфильтровал панель по
одной, KPI покажет **полную** выручку товара, как будто её целиком принесла
эта кампания. Задвоения нет, но ROAS и TACoS в разрезе одной кампании будут
выглядеть лучше, чем эта кампания заслуживает. Исправить на уровне данных
нечем — источник такой. Фронт обязан это проговаривать подписью у KPI, когда
выбран фильтр по конкретной кампании и среди её товаров есть хоть один,
встречающийся в другой кампании.

Существующий `Store.get_metrics_series(sku, days)` фильтрует только по `sku`
и в этом случае вернёт по две точки на день. Эндпоинт `/series` обязан
сворачивать их сам: `cost` и счётчики — суммой, `revenue` — одним значением,
`tacos`/`roas` — пересчётом из свёрнутых сумм, а не усреднением готовых.

## ИИ

### Границы полномочий

Это решение зафиксировано отдельно, потому что оно про деньги.

**ИИ не назначает и не меняет ставки. Никогда, ни в каком режиме.**

Цепочка: ИИ советует → человек нажимает → меняется **настройка** →
`core/rules.py` по своим детерминированным правилам считает новую ставку.

Кнопка «Применить» под рекомендацией дёргает ровно те же эндпоинты, что и
обычная форма настроек — `PUT .../settings` или `PUT .../control`. Никакого
отдельного пути в обход валидации у ИИ нет. Все предохранители (`bid_ceiling`,
`min_bid`, `max_bid_step`, `max_changes_per_day`, пейсинг бюджета) продолжают
работать, потому что ставку по-прежнему считает тот же протестированный код.

Худшее, что может сделать галлюцинация модели — показать владельцу глупый
совет, который тот не нажмёт.

### Как кнопка «Применить» вообще возможна

Из свободного текста кнопку не построить, поэтому разбор товара просит у
модели **структурированный ответ** (`output_config.format` с JSON-схемой):

```jsonc
{
  "summary": "Ставку поднимали четыре раза подряд…",   // текст для человека
  "suggestions": [
    { "kind": "control", "field": "enabled", "value": false,
      "label": "Выключить бота на этом товаре",
      "why": "CR 1,1% — товар не окупится и на минимальной ставке" },
    { "kind": "override", "field": "min_clicks_for_no_cart_cut", "value": 40,
      "label": "Срезать ставку уже после 40 кликов без корзин",
      "why": "сейчас порог 60, защита включается слишком поздно" }
  ]
}
```

Предложение принимается фронтом, только если:

- `kind` — `"control"` или `"override"`;
- для `override` поле входит в `OVERRIDABLE_FIELDS` из `core/config_resolver.py`;
- для `control` поле одно из `enabled`, `window_start`, `window_end`, `days_mask`;
- значение проходит ту же валидацию `core/settings_io.py`, что и ручной ввод.

Предложение, не прошедшее проверку, не показывается кнопкой — только текстом
в разборе. Белый список полей ведём явно: модель не должна иметь возможности
предложить правку поля, которого нет в форме.

Максимум три предложения на разбор — иначе панель превращается в список
кнопок, которые владелец нажимает не читая.

### Разбор товара

`analyst.py` дополняется двумя **чистыми** функциями по образцу уже
существующих `gather_digest` / `build_prompt`:

- `gather_product_digest(store, campaign_id, sku, days)` — метрики по дням,
  история ставки и CPC, лог решений, эффективный конфиг, расписание.
- `build_product_prompt(digest) -> (system, user)`.

Сеть остаётся за инъектируемым `llm_fn`, так что обе тестируются без сети и без
ключа — ровно как дневной разбор сейчас.

Кэш: разбор младше 6 часов отдаётся из `ai_insights`. Параметр `?force=1`
пересчитывает. Ключ кэша — `(kind, scope_id, day)`.

Предохранитель расхода: `AI_DAILY_LIMIT` (дефолт 30) — число реальных вызовов
Anthropic за сутки, считается по `ai_insights` за текущий день. При превышении
API отдаёт 429 и понятный текст, а не молча жжёт баланс.

### Ежедневный разбор

`analyst_job` меняется с «логировать текст» на «писать в `ai_insights`».
Логирование остаётся дополнительно — оно бесплатное и помогает при разборе
инцидентов.

### Модель и цена

Обе задачи — `claude-opus-5`, с адаптивным мышлением
(`thinking={"type": "adaptive"}`), как уже настроено в `analyst.py`. Модель
не понижаем: выбор более дешёвой — решение владельца, а не умолчание разработки.
Тариф Opus 5: **$5 за 1M входных, $25 за 1M выходных токенов**.

Оценка расхода:

| Что | Токенов вход / выход | Цена вызова |
|---|---|---|
| Разбор одного товара | ~4 тыс. / ~2 тыс. | ~$0,07 |
| Ежедневный разбор | ~8 тыс. / ~2 тыс. | ~$0,09 |

При десятке нажатий кнопки в день и одном дневном разборе выходит порядка
**$20 в месяц**. Лимит `AI_DAILY_LIMIT = 30` ставит потолок около $2 в сутки.

Кэш промптов не подключаем: системный промпт короче минимального кэшируемого
префикса, кэш просто не сработает.

### Баг, который правим заодно

В `analyst.py` стоит `max_tokens=2000` вместе с адаптивным мышлением. Токены
мышления считаются внутри `max_tokens`, так что на длинном дне разбор
обрывается на полуслове. Поднимаем до `max_tokens=16000` — это рекомендованный
дефолт для нестримингового запроса, и платим мы за фактические токены, а не за
потолок.

### Ключ и баланс

`ANTHROPIC_API_KEY` живёт только в `config/.env` на сервере, в браузер не
попадает. Сейчас баланс нулевой, поэтому `ANALYST_ENABLED=0`. Пополнение
баланса — действие владельца, вне этой работы. Пока баланса нет, оба
ИИ-эндпоинта возвращают понятную ошибку, а панель показывает её текстом;
всё остальное работает.

## Фронтенд

### Дизайн-токены

Берутся из утверждённого макета: тёплые нейтрали (`#f4f3f0` полотно,
`#ffffff` поверхность, `#1a1a18` чернила), акцент — почти чёрный, семантика
отдельно (зелёный/янтарный/красный). Тёмная тема определена на том же наборе
токенов в трёх состояниях (`:root`, `prefers-color-scheme`, `[data-theme]`).

Синий **зарезервирован за графиками** и не используется в интерфейсе, чтобы
цвет в UI означал ровно одно: состояние метрики.

Шрифт — системный (`-apple-system`, на Маке это SF Pro), плюс системный
моноширинный для кодов товаров и числовых колонок. Внешние шрифты не грузим.

### Экраны

**`/` — Товары.** Шапка (фильтр кампании, период 7/14/30, индикатор тестового
режима), строка KPI на хайрлайнах, сгруппированный список товаров. Строка
несёт: название, код, спарклайн ставки, ставку, TACoS тегом, CTR, ROAS и
тоггл «биддер ведёт товар». Клик раскрывает панель с сегмент-контролом
**Графики / Настройки / Решения** и кнопкой «Разобрать с ИИ». Внизу карточка
ежедневного разбора.

**`/settings` — Настройки биддера.** Глобальные поля, тестовый режим, аудит.

Все чекбоксы заменены тогглами, включая «наследовать» в настройках товара.
Выключенный тоггл «наследовать» открывает поле для ввода.

### Графики

Пишутся как собственный SVG-компонент, без графической библиотеки — набор
форм маленький и полностью известен, а Recharts тянет за собой D3.

1. **Ставка и цена клика** — две линии в ₸ на одной шкале, плюс треугольные
   маркеры правок биддера (вверх/вниз) с причиной в тултипе.
2. **TACoS** — линия с залитым целевым коридором `target_tacos_low..high`.
3. **CTR** и **конверсия в корзину** — два маленьких графика рядом.

Правила, которым следуем (из skill `dataviz`):

- **Никаких двойных осей.** Изначально предлагавшийся график «расход против
  выручки с ROAS на второй оси» отвергнут: 15 тыс. против 222 тыс. на общей
  шкале превращают расход в плоскую линию, а две шкалы вводят читателя в
  заблуждение. Его место занял график TACoS с коридором — это и есть величина,
  которой управляет биддер.
- Цвет серии закреплён за сущностью и не переназначается при фильтрации.
- Текст подписей носит токены чернил, а не цвет серии.
- Кросс-хэйр и тултип по наведению — на всех графиках.
- Палитра проверяется скриптом из `dataviz`, а не на глаз.

## Тесты

Бэкенд — в стиле проекта: `.venv` + самостоятельные скрипты `test_*.py`, без
pytest, запуск `.venv/bin/python test_x.py`.

Новые и переписываемые:

- `test_store.py` — новые колонки снапшота, `metrics_daily`, `ai_insights`,
  идемпотентность upsert, миграция поверх старой БД без потери данных.
- `test_revenue.py` — `collect_for_day` на границах суток Алматы.
- `test_worker.py` — `daily_metrics_job`: запрашивает нужные даты, пересчитывает
  вчера, корректно ведёт себя при пустом ответе кабинета.
- `test_webui.py` — переписывается под JSON API через `TestClient`: коды
  ответов, 401 без сессии, валидация, сохранение оверрайдов и расписания.
- `test_analyst.py` — `gather_product_digest` и `build_product_prompt` на
  подставном `llm_fn`; лимит `AI_DAILY_LIMIT`; попадание и промах кэша.
  Отдельно — фильтр предложений: подставной ответ модели с полем вне белого
  списка, с неизвестным `kind` и с значением, не проходящим валидацию, не
  должен доходить до кнопки. Это тест на деньги, а не на форматирование.

Фронт — Vitest только на чистые функции (форматирование чисел, построение
геометрии графиков, пороги здоровья TACoS). Тестов на рендер компонентов не
пишем: они дороги в поддержке и мало что ловят на проекте такого размера.

Удаляются: `test_search_client.py`, `test_store_positions.py`,
`test_worker_positions.py`, `test_positions_config.py`, `test_webui_positions.py`.

## Сборка и выкат

`.github/workflows/ui.yml` на push в `master`:

1. Node 20, `npm ci`, `npm run build` в `frontend/`.
2. Публикация результата в orphan-ветку `ui-dist` (только содержимое `dist`).

Хватает штатного `GITHUB_TOKEN`; новых секретов ни в GitHub, ни на VPS не
появляется, SSH-ключ сервера в CI не уезжает.

`deploy/update.sh` на VPS:

```bash
git pull
git fetch origin ui-dist
git checkout origin/ui-dist -- webui/static/dist
.venv/bin/pip install -r requirements.txt
sudo systemctl restart kaspi-webui kaspi-autopilot
```

Node на сервере не нужен, история `master` не засоряется собранными файлами.
`webui/static/dist/` попадает в `.gitignore`.

`deploy/DEPLOY.md` дополняется разделом про `ui-dist` и обновлённой командой
выката.

## Порядок работ

Работаем в отдельной ветке: на VPS продолжает крутиться `master` со старой
рабочей панелью, пока не смержим.

| # | Фаза | Результат |
|---|---|---|
| 1 | Данные | миграции схемы, `metrics_daily`, `ai_insights`, `daily_metrics_job`, `collect_for_day` |
| 2 | Зачистка | полное удаление позиционного трекера |
| 3 | API | роутеры `webui/api/*`, снос шаблонов, переписанный `test_webui.py` |
| 4 | Каркас фронта | Vite, токены, оболочка, экран логина, список товаров с тогглами |
| 5 | Панель товара | сегмент-контрол, настройки, решения, графики |
| 6 | ИИ | разбор товара, дневной разбор, кэш и лимит |
| 7 | Выкат | GitHub Actions, `update.sh`, DEPLOY.md |

После фазы 2 и до конца фазы 4 панель внутри ветки не запускается — это
ожидаемое промежуточное состояние, согласовано.

## Чего эта работа НЕ делает

- Не трогает `core/rules.py` и логику принятия решений.
- Не даёт ИИ управлять ставками. ИИ остаётся советчиком: кнопки «Применить»
  под его рекомендациями меняют настройки, и нажимает их человек.
- Не убирает уровень кампании из `core/config_resolver.py` — уходит только экран.
- Не тянет изображения товаров: выбранный Apple-стиль в них не нуждается.
- Не выключает тестовый режим. `dry_run` переключает владелец, когда убедится,
  что новая панель показывает правду.
