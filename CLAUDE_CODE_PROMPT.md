# Проект: Kaspi Ads Autopilot — автоматическое управление рекламными ставками на Kaspi.kz

Ты продолжаешь разработку сервиса, фундамент которого уже заложен. Ниже — весь контекст, согласованные решения, что готово и что делать дальше. Читай целиком перед тем, как писать код.

---

## 1. Что за сервис и зачем

Автопилот рекламных ставок для продавца на Kaspi.kz (маркетплейс, Казахстан). Задача: весь день сам следит за ставками в рекламном кабинете, считает окупаемость по реальной выручке и меняет ставки по правилам — без ручного вмешательства.

Владелец — селлер AYORA (частная марка мелкой бытовой техники). merchantId маркетинга: `832398`. Пример активной кампании: `2711494`. Всё это идёт в конфиг, не хардкодить.

**Модель распространения:** сначала на себя, потом выложить в GitHub, чтобы другие селлеры разворачивали у себя на своём VPS со своими кредами. Поэтому: никаких чужих данных у нас, всё self-hosted, креды только в локальном `.env` на машине владельца. Проектируй с прицелом на «клонируй и подними у себя».

**Хостинг:** VPS (Linux, 24/7). НЕ локальный комп (может выключиться). Воркер под systemd. SQLite на диске.

## 2. Архитектура доступа — ДВА РАЗНЫХ механизма (критично понять)

У Kaspi два разных кабинета, и у нас два разных способа доступа к ним:

### A. Маркетинговый кабинет (ставки) — `marketing.kaspi.kz`
- Официального API НЕТ. Работаем через внутренние JSON-эндпоинты кабинета.
- Авторизация — **cookie-сессия** (протухает). Официального токена нет.
- Отсюда: читаем список товаров кампании со ставками, PUT-им новые ставки.

### B. Основной кабинет продавца (выручка) — `kaspi.kz/shop/api/v2`
- Это ОФИЦИАЛЬНЫЙ Kaspi Shop API. Документация: https://guide.kaspi.kz/partner/ru/shop/api/orders/q3201
- Авторизация — статичный **`X-Auth-Token`** (обычная строка из Настройки → API кабинета). Стабильный, не протухает.
- Отсюда: тянем все заказы за период → считаем реальную выручку по каждому товару.

**Почему нужны оба:** маркетинговый кабинет показывает выручку только по рекламной атрибуции, и она СИСТЕМАТИЧЕСКИ ЗАНИЖЕНА — часть заказов он не видит. Реальную полную выручку по товару даёт только Shop API. Поэтому окупаемость (TACoS) считаем по Shop API, а расход на рекламу (cost) — из маркетинга. Сшиваем два источника по `merchantSku`.

## 3. Ключевые согласованные решения (НЕ переигрывать без явного запроса владельца)

1. **Метрика — TACoS (не маркетинговый crr):**
   ```
   TACoS = cost_рекламы / полная_выручка_по_SKU_из_ShopAPI
   ```
   Это доля рекламных расходов во ВСЕЙ выручке товара (не только рекламной). Целевой порог задаётся в конфиге, он будет НИЖЕ маркетингового crr, т.к. знаменатель больше.

2. **Выручку привязываем к дате СОЗДАНИЯ заказа (`creationDate`), НЕ к доставке.**
   Причина: заказ падает сегодня (реклама сработала сегодня, cost списался сегодня), но после 16:00 он уезжает на доставку завтра. Если считать по доставке — расход и выручка одного клика разъезжаются по дням, TACoS скачет, бот дёргается. Поэтому Shop API фильтруем по `filter[orders][creationDate][$ge/$le]`.

3. **Окно расчёта TACoS — 2 дня** (скользящее, «вчера + сегодня»). Быстро реагирует на ставки, но шумно → предохранители важны. Параметр `tacos_window_days: 2` в конфиге.

4. **Отмены вычитаем, возвраты — нет.**
   - `CANCELLED` / `CANCELLING` → вычесть из выручки (заказ не выкуплен, денег нет).
   - `RETURNED` → НЕ трогать, считается обычной выручкой (при окне 2 дня возврат физически почти не успевает попасть в окно; хендлить возвратный контур решили не усложняя).

5. **Границы дня — по Asia/Almaty**, конвертим в epoch-мс для Shop API.

6. **Сшивка маркетинг ↔ merchant по `merchantSku`.** В маркетинговом ответе это поле `merchantSku` (напр. `432085472`). В Shop API entries это `merchantProduct.code`. Это один и тот же идентификатор.

7. **Двухуровневая логика принятия решений (ВАЖНО — это ядро):**
   - **Быстрый контур** (каждые 15–30 мин, внутридневной) — ТОЛЬКО ТОРМОЗИТ, не разгоняет. Защита от слива бюджета. Триггеры, которые НЕ запаздывают:
     - `costToday > дневной_лимит_SKU` → пауза до завтра
     - `avgCpc` подскочил > X% → срезать шаг вниз
     - `clicks > N И carts == 0` → срезать (ОБЯЗАТЕЛЬНО порог по объёму, не «0 продаж на 5 кликах», а «0 корзин на 40+ кликах»)
     - низкий `score` товара → не задирать ставку выше рынка
   - **Медленный контур** (1–2 раза в день, по TACoS_2d) — РАЗГОНЯЕТ по окупаемости:
     - TACoS в коридоре → держим
     - TACoS ниже коридора → можно поднять (реклама дёшево окупается)
     - TACoS выше коридора → снижаем
   - **Железный принцип: быстрый контур только режет/тормозит, медленный только разгоняет.** Разгон на быстром внутридневном сигнале — ГЛАВНАЯ ошибка: конверсия внутри дня всегда выглядит плохо утром (cost капает непрерывно, заказы приходят пачками вечером и с лагом из-за «после 16:00 на завтра»). Бот, который режет ставку в 11:00 из-за «потратил, продаж нет», сам себе рубит вечерние продажи. НЕ ДЕЛАТЬ ТАК.

8. **ИИ как второй слой, не в петле.** Ядро решений — детерминированные правила (прозрачно, аудируемо, дёшево, на живом бюджете предсказуемо). LLM навесить ОТДЕЛЬНО как «аналитика»: раз в день читает логи и человеческим языком объясняет, что произошло и что подкрутить, плюс подсвечивает аномалии. НЕ отдавать LLM руль над ставками, пока правила не обкатаны.

9. **Куки маркетинга — автологин через Playwright.** У владельца на входе НЕТ SMS/2FA (только логин+пароль), поэтому полный автологин возможен: Playwright headless логинится сам, сохраняет `storage_state`, продлевает сессию. НО: если Kaspi вдруг покажет неожиданный экран (SMS/капча/подтверждение нового устройства с нового VPS-IP) — воркер НЕ крутится вслепую, а ОСТАНАВЛИВАЕТСЯ и шлёт алерт владельцу «нужен ручной вход». Не ломаться молча.

10. **Предохранители (в конфиге, обязательны из-за окна 2 дня):** потолок ставки, макс. шаг изменения за тик, макс. число изменений в день на SKU, dry-run режим, полный лог каждого решения с причиной. На старте — dry-run: считает и логирует решения, PUT не шлёт, пока владелец не убедится глазами.

Запуск теста: `python3 test_revenue.py` — должен пройти без ошибок.

**ОДНО НЕПОДТВЕРЖДЁННОЕ МЕСТО:** в `get_order_entries()` точное имя поля с merchantSku внутри ответа `/orders/{id}/entries` угадано тремя вариантами (`merchantProductCode` / `offerCode` / `code`). Проверить на РЕАЛЬНОМ ответе Shop API (сделать один запрос своим токеном, посмотреть JSON) и поправить, если поле называется иначе. Это правка в одну строку.

## 5. Что делать дальше (порядок)

### Шаг 1 — `connectors/marketing_client.py` (следующий по плану)
Чтение ставок + PUT новой ставки. Реальные эндпоинты (проверены на живом кабинете):

**Чтение товаров кампании (GET):**
```
GET https://marketing.kaspi.kz/advertising/products/api/v5/merchant/{merchantId}/campaign/{campaignId}/products?StartDate=YYYY-MM-DD&EndDate=YYYY-MM-DD
```
Ответ: `{result:"Ok", data:[...]}`. По каждому товару важные поля:
- `sku` (напр. "166350900"), `merchantSku` (напр. "432085472" — КЛЮЧ сшивки с выручкой)
- `campaignProductId`, `bid` (текущая ставка), `avgCpc` (реальная цена клика — может быть НИЖЕ bid)
- `score` (0–10, качество товара в рекламе), `buyBox` (bool), `productState` (Active/Paused/OutOfStock)
- обратная связь: `cost`, `costToday`, `gmv`, `crr`, `cr`, `ctr`, `views`, `clicks`, `carts`, `transactions`, `price`
- ВАЖНО: позиции в выдаче и ставок конкурентов в ответе НЕТ. Автопилот управляет по ЭКОНОМИКЕ (TACoS, avgCpc, cart-rate), а НЕ по позиции. Это осознанное ограничение.

**Обновление ставки (PUT):**
```
PUT https://marketing.kaspi.kz/advertising/products/api/v1/merchant/{merchantId}/campaign/{campaignId}/products/update-bid
body: {"skuList":["166350900"], "bid":20}
```
Принимает МАССИВ sku → можно батчить в одном запросе. Ключ здесь — `sku` (НЕ campaignProductId). Заголовки, которые кабинет шлёт и которые стоит воспроизвести: `X-Front-Version`, `X-Requested-With: XMLHttpRequest`, `Content-Type: application/json`, `Origin`/`Referer` на marketing.kaspi.kz.

`marketing_client` должен ПРИНИМАТЬ сессию/куки извне (от session_manager), не добывать их сам — так клиент не зависит от способа авторизации.

### Шаг 2 — `session_manager.py` (Playwright)
Автологин на marketing.kaspi.kz по логину+паролю из `.env`. Сохранение/переиспользование `storage_state`. Продление сессии. Детект неожиданных экранов (SMS/капча) → алерт + стоп, не крутиться вслепую. Отдаёт свежие куки для marketing_client.

### Шаг 3 — `core/reconcile.py`
Сшивка: cost (маркетинг) ⨝ выручка (revenue.py) по merchantSku → TACoS_2d по каждому SKU.

### Шаг 4 — `core/rules.py`
Движок правил: быстрый контур (тормозит) + медленный (разгоняет по TACoS). Все пороги из `config/rules.yaml`. Каждое решение возвращает (sku, старая_ставка, новая_ставка, причина) для лога.

### Шаг 5 — `worker.py`
Два независимых расписания (APScheduler):
- ставочный тик (15–30 мин): read маркетинг → взять выручку из кэша → rules → PUT (или dry-run) → лог
- цикл выручки (реже, напр. раз в час): тяжёлый обход Shop API → обновить revenue_cache в SQLite
SQLite-таблицы: products_snapshot, revenue_cache, decisions_log, tacos_daily.

### Шаг 6 — LLM-аналитик (отдельно, не в петле)
Раз в день читает decisions_log + метрики, пишет человеческий разбор и аномалии. Можно через Anthropic API.

### Шаг 7 — обвязка
`config/.env.example`, `config/rules.yaml`, systemd-юнит, README с инструкцией разворачивания для селлера, `.gitignore` (креды, storage_state, *.db, .env).

## 6. Стек и правила

- Python 3.12. `httpx` (HTTP), `APScheduler` (расписание), Playwright (автологин), SQLite (stdlib), `PyYAML` (конфиг).
- Все креды — только из окружения/`.env`. НИКОГДА не хардкодить, не логировать токены/пароли/куки.
- Kaspi может блокировать аккаунты (клаузула 5.3.13). Поэтому: консервативные дефолты, широкие предохранители, dry-run на старте, полный аудит-лог. Первые дни бот считает и логирует, но НЕ шлёт PUT, пока владелец не проверит решения глазами.
- Осторожно с частотой запросов к обоим кабинетам (429). Ретраи с бэкоффом уже есть в merchant_client — повторить подход в marketing_client.
